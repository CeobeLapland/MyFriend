# ADR 0025 — Studio 应用：UI 形态、配置读写与动画配置归属

> 本文对应 `.trae/documents/studio-app.md` §7 的三个决定点与 §10 的未决问题；
> 是 `docs/08` §12 所说"产品 UI 需要独立的技术选型与设计，届时另开 ADR"的那份 ADR。
> 四项用户拍板结论来自本轮 `AskUserQuestion`（均按推荐项采纳）：
> **Web UI 先行 / 配置写 `.env` + 重启 / 动画后端托管 / 语音先文本后语音**。
> 配套实施计划：`.trae/documents/studio-implementation.md`（阶段 1）。

## Decision

### 1. 产品 UI 走 **Web UI 先行**（A → C 两步，跳过 Unity 一体化）

Studio 的界面形态：**后端托管一个零构建的产品级网页**（`GET /studio`），浏览器打开即用。
将来若要"独立应用窗口 + 系统托盘 + 进程管理"，再给这个网页套桌面壳（Tauri / PyWebView），
**前端代码不重写**。**不做** Unity 一体化外壳（UI Toolkit 方案）。

理由：

- **零新增依赖**：单文件 HTML + 原生 JS，沿用 ADR 0017 已验证的做法（符合 `AGENTS.md`
  "先看现有依赖能不能解决"）。
- **它就是桌面壳的前端**：先做网页不浪费任何工作——套壳只是把它装进 WebView。
- **UI 与形象天然分离**：形象窗口（Unity）该能全屏 / 置顶 / 透明，UI 该在需要时才出现；
  一体式是直播工具（VTube Studio）的形态，不是陪伴应用的形态。
- 记忆列表、配置项、模型下拉这类**表单密集型界面**是网页的主场；用 Unity 做成本显著更高，
  且形象表现力已经沉淀在 Unity 侧（M5 的 `ANIMATION.md` + 15 个 .cs），搬 UI 不会带来任何简化。

**已知代价**（用户已确认接受）：形象在 Unity 窗口、界面在浏览器，是两个窗口。

### 2. 配置的读写：**写 `.env` + 一键重启后端**，不做运行时热更新

Studio 修改配置（LLM / embedding / STT / TTS 的 provider 与模型、音色参考音频等）的方式是：
**只改 `.env` 里对应键的值，然后重启后端进程**。不做 `PUT /v1/settings` 式的运行时可变配置。

理由：

- **实测重启成本 ≈ 1~2 秒**（本轮实测：uv 起到 uvicorn 可应答；`Application startup complete`
  与 `Started server process` 只差 8ms，耗时都在 uv 与环境装配上）——一键重启体验代价极低。
- `Settings` 是启动期读一次（`lru_cache`），做热更新要改它的生命周期；
  M4 才拆过 settings 包（5 个 mixin），**风险明显大于收益**。
- `.env` 保持**唯一真相**：可手改、可备份、可复制；Studio 只是"编辑这份真相的界面"
  （studio-app.md §11 风险 1：Studio 不能变成第二套真相）。

**实现约束**：`Settings` 使用 `extra="forbid"`——写 `.env` 时**只允许改已知键的值**，
不许增删键（多一个键 = 后端启动直接失败）；并**保留原文件的分组注释与顺序**
（用户会手看这个文件）。`.env` 不存在时先从 `.env.example` 复制。

### 3. 动画映射归**后端托管**（Unity 改为从后端拉取），放阶段 3 实施

`astra_animation.json` 的归属：**后端提供读写端点、持有权威配置；Unity 启动 / 重连时
从后端拉取，本地文件仅作兜底缓存**。

理由：

- Studio 的"一个界面管全部"要求它能改动画映射；托管后 Studio 天然可改，
  且**不需要把 Unity 工程的机器专属绝对路径写进配置**（studio-app.md §7.3 方案 a）。
- 单一真相：现状是配置只存在 Unity 工程里，Studio 与它互不认识。

**已知风险（实施时必须处理）**：

- Unity 工程不是 git 仓库（ADR 0024 §9）——改 Unity 源码前**先备份文件**。
- Unity 端会新增一处对后端的依赖：后端不可用时**必须回退到本地缓存**，
  不能变成"打不开后端就没有动画"。

### 4. 语音对话做进 Studio（**先文本后语音**）

"一个界面管全部"包含语音，所以语音对话要在 Studio 内实现（声音采集 / 播放 / 打断，
移植 `/dev` 已工作的逻辑）。**排期在文本功能稳定之后**（阶段 3）：
聊天 / 状态 / 记忆是本体的核心闭环，先把它们做扎实。

### 5. 产品 UI **无条件挂载**（`GET /studio`），与 `/dev` 并存

- `/dev` 保持现状：只在 `ASTRA_ENV=dev` 挂载（ADR 0017），**不删、不改**——
  它是协议层的开发工具，产品 UI 做出来之后依然有用。
- Studio 是应用本体，**不受 `ASTRA_ENV` 门控**：设成 prod 也照常可用。
  安全边界本来就靠默认绑定 `127.0.0.1`（ADR 0002 单进程本地）；
  若把服务绑到 0.0.0.0，`/v1` API 本身就没有鉴权，单独给一个 UI 页面加门控并无额外收益。

### 6. 显存状态 = **加载状态实测 + GPU 归属声明式**（本轮实测结论）

关闭 studio-app.md §10#6 的实测项。实测结果：

| 想要的信息 | 能不能实测 |
|---|---|
| 模型**是否加载**、identifier、上下文长度、大小 | ✅ `lms ps --json`（已加载模型）/ `GET /api/v0/models`（含 `state: loaded/not-loaded`） |
| 模型在 **GPU 还是 CPU** | ❌ 两个接口都**没有**该字段（`ps --json` 里最近的是 `deviceIdentifier`——那是 LM Link 远程设备槽，本地加载时为 `null`） |

所以 Studio 的显存策略功能设计为：

- **加载状态**：实测（`lms ps --json` / REST），如实显示"已加载 X（ctx 16384）"。
- **GPU / CPU 归属**：Studio **记录自己最后一次下发给 `lms load --gpu` 的参数**，
  UI 上标注这是"声明值"而非"实测值"——因为模型可能在 Studio 之外被重新加载。

## Reason

- **为什么跳过 Unity 一体化（B）**：见 §1。补充：UI 的迭代频率远高于形象，
  分开后改界面不用进 Unity 重编译；且"两个窗口"本来就是形象沉浸 / 界面克制的分工。
- **为什么配置不做热更新**：见 §2。另：把配置放进数据库（方案 c）会制造第二份真相，
  违反 `docs/03` 的"配置文件 vs 数据"边界。
- **为什么动画托管放阶段 3**：Unity 面板现在能用（用户在配 46 个动画的映射），
  这条改动会让后端成为 Unity 的运行时依赖——值得排在核心体验（对话 / 状态 / 记忆）之后。

## Consequences

- `docs/08` §12 的"届时另开 ADR"落地为本文；实施完成后 README 增补 Studio 段落，
  `docs/08` §12 补"实际落点"。
- **阶段 1 零新增后端业务端点**：Studio 第一版只用既有 HTTP / WS 接口
  （对话 / 状态 / 记忆 / health 全部已就绪），后端改动只有"加一个静态页路由"。
- **配置写入是"改值不改键"**：实现时对照 `.env.example` 的已知键清单；
  写错键名会让后端下次启动直接失败（`extra="forbid"`）。
- **动画映射端点设计留到阶段 3**（存储位置、缓存回退策略届时再定并另记 ADR 或补充本节）。
- **桌面壳（阶段 4）不在本 ADR 承诺范围内**：A 做完后按当时的实际需要再决定。
- **`/studio` 与 `/dev` 的挂载规则相反**（无条件 vs 仅 dev）：
  这一点要用测试显式钉住，防止将来有人"顺手"把 Studio 也门控掉（或把 /dev 放开）。
