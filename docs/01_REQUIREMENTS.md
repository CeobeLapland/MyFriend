# 01 Requirements

## 1. 产品目标

Astra 是一个长期存在于本地设备上的 AI Companion。用户可以通过文字或语音与其交流；Astra 具有稳定的人格、可持续更新的记忆、可解释的情绪/状态，以及一个能够通过表情、口型和动作表达这些状态的 3D Avatar。

产品体验目标不是“回答得最聪明”，而是：

- 回复自然且稳定。
- 前后人格一致。
- 能记住真正重要的事情。
- 能区分“刚刚发生的事”和“长期事实”。
- 说话有连续性和低等待感。
- 角色身体表达与语言状态一致。
- 用户可以查看、修改和删除记忆。
- 用户可以控制 AI 能做什么。

## 2. 功能分级

### P0：必须完成

1. 文本聊天。
2. LLM Adapter。
3. Persona 配置。
4. Conversation 管理。
5. SQLite 持久化。
6. Memory 提取与检索。
7. Structured Response。
8. Emotion State。
9. Tool Registry 基础设施，但初始只允许无副作用工具。
10. WebSocket 事件通道。
11. 基础 Unity/VRM 客户端。

### P1：完成后明显提升体验

1. Streaming LLM。
2. STT。
3. Streaming/low-latency TTS。
4. Lip Sync。
5. Idle Animation。
6. 主动行为调度。
7. Relationship State。
8. Tool Calling。
9. 记忆管理 UI。
10. 角色状态 UI（情绪、当前行为、设备连接状态）。

### P2：增强功能

1. 屏幕视觉理解。
2. Computer Use 的受控子集。
3. 任务/提醒。
4. 日记与回忆摘要。
5. ComfyUI 生成“纪念图片/场景图”。
6. 多设备客户端。
7. 语音打断。
8. 声线/语气 Profile。
9. 多模态输入。

### P3：实验性

1. 自主长期任务。
2. 基于场景的复杂动作规划。
3. 端到端实时语音模型。
4. 可持久化环境状态。
5. 强化学习或微调。

## 3. 非功能需求

### 性能目标

在本地硬件允许范围内：

- UI 文本首响应尽快出现；不要强制等待完整生成。
- TTS 应尽量支持首包即播。
- Avatar 端保持稳定帧率；默认目标 60 FPS，低配场景允许降级。
- Memory 检索应与 LLM 生成并行或尽可能提前执行。

### 稳定性

- 单个外部服务不可用时，整个系统仍应允许降级运行。
- Unity 挂掉不应导致 AI Core 崩溃。
- TTS 不可用时仍显示文本。
- STT 不可用时仍允许键盘输入。
- Memory DB 暂时不可用时，至少允许当前会话继续运行（需记录 degraded mode）。

### 可维护性

- 所有模型/服务使用 Adapter。
- 所有事件使用 versioned schema。
- 所有对外协议由 JSON Schema 描述。
- 禁止在业务逻辑中直接散落 HTTP 请求。

## 4. 用户体验原则

1. 不要每个动作都调用 LLM。
2. 不要为了“像人”而假装拥有真实感受；角色状态是软件状态。
3. 避免重复询问用户已经提供的信息。
4. 记忆相关回复要能被追溯到实际存储的记忆。
5. 当工具失败时，要自然地告诉用户发生了什么，而不是编造成功结果。
6. 被打断时优先停止 TTS 和长任务，进入新的 turn。
