## 0. 一句话

把**后端 / 文本 / 语音 / Unity / 配置**整合成一个能真正用起来的桌面应用 ——
现在的启动流程要开 4 个进程、配 6 个环境变量，界面散在 3 个地方互不认识。

## 1. 为什么做（痛点要具体）

### 1.1 现在的启动流程

```powershell
# 手动开 4 个东西 + 配一堆环境变量
1. LM Studio（手动加载模型；还要决定 --gpu max / off，见 §3.5）
2. CosyVoice 雨落版 Gradio 应用（手动启动，localhost:7860）
3. uv run astra serve （+ 6 个环境变量内联指定）
4. Unity 编辑器 → 按 Play
```

忘一个就有一个功能静默降级（`/health` 会说，但没人会去开浏览器看它）。

### 1.2 界面散在三个地方，互相不认识

| 界面 | 位置 | 能看到什么 | 改不了什么 |
|---|---|---|---|
| 开发者控制台 | 浏览器 `GET /dev` | 对话、事件流、health、记忆面板、状态面板、协议词表 | 除了记忆开关，什么配置都改不了 |
| Unity 配置面板 | Unity 里按 Play | 形象、站姿、表情强度、动画映射 | 后端的一切 |
| 环境变量 / 文件 | 手动编辑 | `.env` / `persona.toml` / `astra_animation.json` | — |

**M6/M7 加的能力越多（工具调用、主动行为），这个割裂越痛。**

### 1.3 文档里本来就有位置

`docs/01` §2 的 **P1** 明确列了两条：

```
9.  记忆管理 UI。
10. 角色状态 UI（情绪、当前行为、设备连接状态）。
```

而 `docs/08` §12 说：

> **产品 UI**（角色形象、对话气泡、设置页）仍然属于 P1/P2，需要独立的技术选型与设计，届时另开 ADR。

⇒ **Studio 不是偏航，正是文档里被推迟的那部分。** 但它需要 ADR。

## 2. 目标与非目标

### 2.1 目标

1. **一键启动**：一个按钮把 LM Studio / CosyVoice / 后端都拉起来，并如实显示每个组件的状态
2. **一个界面管全部**：对话、角色状态、记忆、配置（API / 模型 / 人格 / 语音 / 动画）
3. **可配置**：改 provider（本地或外部API）、模型、音色、人格、动画映射**不用碰文件**
4. **好看、能用**：这是用户第一次要"产品级"的界面，不是开发工具

### 2.2 非目标（这一版不做）

- **不做多用户 / 联网部署**（ADR 0002 单进程本地）
- **不做移动端**
- **不重写后端**：Studio 是**后端之上的壳**，不改 API 契约
- **不做音频/动画的算法改动**：那是客户端的事，Studio 只做"配置它们"

## 3. 现状盘点（新上下文需要知道的全部事实）

### 3.1 后端已有的 HTTP / WS 接口（**基本够用，缺"写配置"**）

```
GET  /health                                   # 5 个固定 key，HTTP 恒 200
GET  /v1/config                                # 非敏感配置 + 词表
POST /v1/chat/messages                         # 202 投递即返回，结果走 WS
POST /v1/chat/turns                            # 200 同步跑完一整轮
POST /v1/conversations                         # 201 显式开新会话
GET  /v1/conversations/{id}/messages           # 历史（未知会话 404）
GET  /v1/memories                              # 列表 / 过滤 / ?query= 语义检索
GET/PATCH/DELETE /v1/memories/{id}             # 看 / 改 / 真删
POST /v1/memories/clear                        # 清空
GET  /v1/memories/export                       # 导出 JSON
GET/PUT /v1/memories/settings                  # 启用开关（**运行时生效，不用重启**）
GET  /v1/state                                 # 7 维情绪 + 5 维关系（只读）
WS   /ws/v1/session/{session_id}               # 实时事件流 + 音频二进制帧
GET  /dev                                      # 开发者控制台（仅 ASTRA_ENV=dev）
```

**⚠️ 缺的是"写配置"**：除了 `PUT /v1/memories/settings`，**没有任何写端点**。
而 `Settings`（LLM/embedding/STT/TTS 的 provider 与模型）是
**启动期读一次**（`get_settings()` 带 `lru_cache`），**运行时不生效**。

⇒ Studio 改配置 = **写 `.env` + 重启服务**，或者新做一套"运行时可变配置"。
**这是要写进 ADR 的决定点之一（见 §7.2）。**

### 3.2 配置文件都在哪

| 文件 | 内容 | 谁读 | 改法 |
|---|---|---|---|
| `.env`（从 `.env.example` 复制） | 全部 `ASTRA_*` 环境变量（≈40 个） | `Settings`（`extra="forbid"`） | 写文件 + 重启 |
| `personas/astra.toml` | 人格：身份/性格数值/说话风格/行为规则/降级话术 | 后端（stdlib `tomllib`） | 写文件 + 重启 |
| `data/astra.db` | SQLite（消息、记忆、状态、向量索引） | 后端 | **只通过 API 改，不要直接写库** |
| `Assets/StreamingAssets/astra_animation.json` | Unity 的动画映射（待机池 / 动作映射 / 姿态三件套） | **Unity 客户端** | 面板写，或直接改文件 |

**⚠️ `extra="forbid"` 是个硬约束**：`.env` 里出现一个 `Settings` 没有的键 → **启动直接失败**。
Studio 写配置时必须只写已知的键（可以从 `/v1/config` + 一份后端导出的 schema 拿）。

### 3.3 Unity 客户端能做什么、不能做什么

| | |
|---|---|
| **能** | 读 `GET /v1/config`（词表 + `avatar_enabled`）、WS 收发、播音频、驱动表情/动作/口型 |
| **不能** | **写任何东西**（没有写端点）；不知道自己被 Studio 管着 |
| **配置来源** | 后端地址与模型文件名硬编码在 `AstraConfig.cs`（**改它要重编译**） |
| **动画映射** | 存在 Unity 工程里（`Assets/StreamingAssets/astra_animation.json`） |

⇒ **Studio 要管动画映射，必须二选一**（见 §7.3）：
① 后端托管这份配置（多一组端点 + Unity 改成从后端拉）
② Studio 直接写那个 json 文件（要知道 Unity 工程路径）

### 3.4 进程与端口清单

| 进程 | 端口 | 提供 | 启动方式 | 能否被代码管理 |
|---|---|---|---|---|
| LM Studio | `localhost:1234` | LLM（`/v1/chat/completions`）+ embedding | 手动 / `lms` CLI | ✅ 有 REST API 与 `lms` CLI |
| CosyVoice 雨落版 | `localhost:7860` | STT + TTS（Gradio） | 手动启动 exe/脚本 | ⚠️ 只能启动那个进程，没有管理 API |
| astra 后端 | `127.0.0.1:8000` | 全部业务 | `uv run astra serve` | ✅ 自己就是它 |
| Unity 客户端 | — | 形象 | 手动按 Play | ⚠️ 可以 `Unity.exe -projectPath ...` 启动，但**不能控制它按 Play**（开发期用户手动） |

### 3.5 硬件约束（贯穿全局）

**GPU 只有 8GB（RTX 4060 Laptop）**。M4 实测：
**LM Studio 的 LLM 和 CosyVoice 不能同时常驻 GPU 且都快**。

```powershell
lms load nvidia/nemotron-3-nano-4b --gpu off --context-length 16384   # 语音场景
lms load nvidia/nemotron-3-nano-4b --gpu max                          # 纯文本场景
```

⇒ **这是 Studio 最有价值的功能之一**：一键切换显存策略 + 如实显示当前状态。
但注意：**`/health` 检测不到"模型在 GPU 还是 CPU"**（LM Studio 不暴露），
所以 Studio 要么用 `lms ps`（CLI）查，要么把这个开关做成"用户声明"而不是"实测"。**这是决定点。**

### 3.6 对话与语音的现状

- **对话**：文本走 `POST /v1/chat/messages`（202）或 `/v1/chat/turns`（同步）；结果走 WS
- **语音输入**：只有浏览器 `/dev` 实现了（16 kHz mono int16 + 二进制帧 + push-to-talk）
- **语音输出**：由 `session.voice_mode.set` 开关触发，`tts.started` + 二进制帧 + `tts.completed`
- **打断**：新输入会取消在跑的 turn，发 `turn.interrupted`，客户端必须**立即停播**
- **Unity 端不做麦克风采集**（M5 范围决定）

⇒ Studio 要做语音对话，**可以直接把 `dev.html` 的音频逻辑移植过来**（它是可工作的参考实现）。

## 4. 硬约束（不能违反的）

| 约束 | 来源 |
|---|---|
| 后端 provider-agnostic：**不许在业务逻辑里散落 provider 专有 API** | ADR 0001 |
| `/health` 固定 5 个 key、HTTP 恒 200 | ADR 0006 |
| `/v1/config` 的 **key 集合不可变** | ADR 0016 / M4 |
| `.env` 与 `Settings` 必须同步（`extra="forbid"`，多一个键就启动失败） | ADR + M0/M1/M2 踩过 |
| 记忆/状态**只通过 API 改**，不直接写库 | `docs/03` |
| 产品 UI 需要**独立技术选型 + 另开 ADR** | `docs/08` §12 |
| 用户**讨厌过度设计**：三个相似的行内代码好过一个提前抽出来的抽象 | `HANDOFF_2` §1 |
| 依赖面尽量小；先看 stdlib 能不能解决 | `AGENTS.md` |
| 开发者控制台是**开发工具**，产品 UI 出来后它**依然有用**（不要删） | ADR 0017 |

## 5. 架构候选与推荐

### 5.1 三个候选

| | 方案 | 优点 | 缺点 | 新增依赖 |
|---|---|---|---|---|
| **A** ⭐ | **Web UI**：把 `/dev` 升级成产品级，后端提供静态页面，浏览器打开 | **零新增依赖**、UI 想多好看有多好看、改一行刷新即见、和后端同进程共享配置、跨平台 | **多一个浏览器窗口**（和 Unity 并存） | **无** |
| B | **Unity 作为应用外壳**（像 VTube Studio / VSeeFace）：UI Toolkit 做全部界面 | **一个窗口**形象 + UI；可做透明背景 + 置顶（桌面宠物） | Unity 做表单/列表 UI **很痛苦**；配置界面要重写一遍；配置还得绕 HTTP | 无（但工作量大） |
| **C** | **桌面壳**（Tauri / Electron / PyWebView）+ Web UI + 管理子进程 | 一个窗口 + 系统托盘 + **一键启动/管理所有子进程** + 能读 `lms ps` 等本地命令 | **引入新工具链**（Tauri 要 Rust；Electron 很重） | 有 |

### 5.2 推荐：**A → C 两步走，跳过 B**

**为什么 A 先做**
- **零依赖**：符合"先看 stdlib / 现有依赖能不能解决"
- **立刻能用**：做完当天就能用起来
- **它就是 C 的前端**：C 只是给 A 套个壳 + 加进程管理器 → **A 做完再决定要不要 C，一点工作都不会浪费**

**为什么跳过 B**
- Unity 不适合做**表单密集型** UI（记忆列表、配置项、模型下拉），那是 web 的地盘
- **形象窗口和 UI 窗口分开其实是优点**：
  形象该能全屏 / 置顶 / 透明（沉浸），UI 该在需要时才出现（控制）
  —— VTube Studio 那种一体式是为了**直播**，不是为了**陪伴**
- 后端配置要通过 HTTP 绕一圈，而它本来是 Python 对象

> ⚠️ 但这条**要用户认可**。如果用户要的是"一个窗口里形象 + UI"，
> 那就得走 B，或者接受 C 里的"Unity 当独立窗口由 Studio 管理"。

│                                              │  状态栏             │
│              对话区                          │  ● 后端  ok         │

│                                              │  ● STT   not_conf   │

## 7. 要写进 ADR 的决定点（**开工前必须先定**）

### 7.1 UI 技术栈

见 §5。**推荐 A → C，跳过 B**。需要用户认可"两个窗口"是否可接受。

### 7.2 配置的读写方式（**这是最实的难点**）

`Settings` 是**启动期读一次**的（`lru_cache`）。要能改配置，有三条路：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **a** ⭐ | **Studio 写 `.env` + 重启后端** | 零后端改动、`.env` 是单一真相、可手改可备份 | 改一项要重启（后端启动很快） |
| b | 后端做"运行时可变配置"（`PUT /v1/settings` + 不重启生效） | 体验最好 | **要改 `Settings` 的生命周期**（现在是 frozen 的 `lru_cache`），改动大、风险高 |
| c | 把配置放进数据库，Settings 从库读 | 统一 | 又多一份真相，违反 `docs/03` 的"配置文件 vs 数据"边界 |

**推荐 a**。理由：后端启动是秒级的；`.env` 的可手改/可备份特性对本地优先的项目很重要；
而且 b 会动到已经稳定的 `Settings` 装配（M4 刚拆过包）。

**注意**：写 `.env` 时要**只写已知的键**（`extra="forbid"`），
并且**不能把注释和分组搞乱**（用户会手看这个文件）。建议保留原文件结构与注释，只改值。

### 7.3 动画配置的归属

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **a** | **后端托管**：`GET/PUT /v1/avatar/animation`，Unity 改成从后端拉 | 单一真相、Studio 天然能改、**Unity 也不再需要那个本地面板** | 要改 Unity 客户端 + 后端加端点；Unity 工程路径不再重要 |
| b | Studio 直接写 Unity 工程的 `astra_animation.json` | 零后端改动 | Studio 要知道 Unity 工程路径（机器专属的绝对路径，**违反"不把机器专属路径写进配置"**的精神） |
| c | 保持现状（只在 Unity 面板里改） | 零改动 | Studio 的"一个界面管全部"就不成立了 |

**推荐 a**，但**它可以放到 P1**——因为 Unity 面板已经能用，
而且方案 a 会让 Unity 客户端多一处依赖后端（耦合变高）。**需要用户权衡。**

### 7.4 进程管理的边界

- **后端自己**：容易（就是当前进程/子进程）
- **LM Studio**：有 `lms` CLI 与 REST API，可管
- **CosyVoice 雨落版**：**没有管理 API**，只能"启动那个 exe/脚本"，**进程退出的判定要靠端口探测**
- **Unity**：可以 `Unity.exe -projectPath` 启动，但**开发期"按 Play"必须用户手动**
  （Studio 无法控制编辑器 UI）

⇒ **建议**：P0 只做"**如实显示状态 + 一键重启后端**"，
"帮我启动 LM Studio / CosyVoice" 放 P1，且**只做启动，不做强杀**（避免搞坏用户的显存状态）。

## 8. 分阶段实施建议

### 阶段 1：ADR + Web UI 骨架（**先做这个**）

1. **写 ADR 0025**：UI 技术栈 + 配置读写方式 + 动画配置归属（§7 的三条）
2. 后端加静态页（新目录 `src/astra/api/static/studio/`，或单文件起步）
3. 实现 P0 #1–#4（对话 / 状态 / 记忆 / health）
4. **保留 `/dev` 不动**（ADR 0017：它做出来之后依然有用）

**验收**：能在一个页面里聊天、看状态、管记忆、看 health。

### 阶段 2：配置与进程

5. 实现 P0 #5–#6（配置读写 + 重启后端，按 §7.2 的方案 a）
6. 实现 P1 #8–#9（模型下拉 + 显存策略）
7. 实现 P1 #12（启动 CosyVoice / LM Studio）

**验收**：改 LLM 模型不用碰文件；一键重启；健康状态如实反映。

### 阶段 3：语音 + 动画

## 10. 未决问题（**开工前要问用户**）

1. **两个窗口能接受吗？**（形象在 Unity 窗口 + UI 在浏览器窗口 / 或桌面壳）

3. **动画映射放哪？**（§7.3）后端托管（要改 Unity）还是继续留在 Unity 面板？

## 11. 风险

1. **别把 Studio 做成"第二套真相"**：配置的唯一真相是 `.env` / `persona.toml` /
   数据库。Studio 是**编辑这些真相的界面**，不是新的一份存储。
2. **`extra="forbid"`**：写 `.env` 时多写一个键 → **后端启动直接失败**。
   写之前先对比一份已知键清单。
3. **`/v1/config` 与 `/health` 的 key 集合不可变**：Studio 不要依赖"新增 key"来传信息。
4. **前端复杂度会失控**：这是第一个**纯前端**的里程碑。
   建议**零构建起步**（单文件 HTML + 原生 JS，沿用 ADR 0017 的做法），
   等确认要做桌面壳了再考虑引入前端工具链。**否则会为了一个设置页引入 npm 生态。**
5. **进程管理容易搞坏状态**：强杀 CosyVoice 会让显存状态不可预测。
   建议 P0 只做"启动 + 状态显示"，不做"强杀"。
6. **Unity 客户端源码不在 git 里**（ADR 0024 §9）。如果 §7.3 选了方案 a（后端托管动画配置），
   改 Unity 会**没有版本历史兜底**——改之前先备份那个文件。
7. **不要重复实现 `dev.html` 已有的东西**：它的音频逻辑（16 kHz 采集、二进制帧、
   按 `sample_rate` 建 AudioContext、`turn.interrupted` 立即停播）是**可工作的参考实现**，
   照逻辑移植即可（别照抄，它是零构建的原生 JS）。
